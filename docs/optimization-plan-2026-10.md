# 发票助手优化任务单（2026-10）

本文是交给执行方（Codex）的任务单。目标：上传识别更快、识别结果更可信、日常核对更省事。只改发票助手相关代码，不扩展新业务。

## 基线（2026-10-24，未改代码时）

- 完整 pytest：串行通过，约 23.5 分钟，含若干 skip；最慢单测约 12.9 秒，集中在 Agent 测试。
- mypy：通过，106 个源码文件。
- 测量方法：复制工作区数据库到临时目录，原件只读；禁用邮箱、GLM、Jev、飞书。

| 现象 | 实测 |
| --- | --- |

| 同一张图重复 OCR | 入库、费用分类（`expense_classifier.py` 的 `collect`）、外卖报销包导出（`reimbursement.py`）、Agent（`agent_evidence.py`）各自调用 `read_receipt`，没有缓存 |

## 阶段 A：速度

### T0 基线提交

- 逐一检查未跟踪文件和目录（含 `.workbuddy/`、`agent-harness/`、`android/`、`skills/`、`scripts/`）是否含真实姓名、电话、地址、税号、票据、工作区状态、凭据或私人路径。
- 私人内容不提交：按需补 `.gitignore`，或保持未跟踪。在验收报告里列出排除了哪些、原因是什么。
- 其余代码、测试、文档作为一次基线提交，作为后续验收的对比起点。

### T1 OCR 结果缓存

- 按“原图字节 SHA256 + 引擎签名”缓存 `read_receipt` 的结果。引擎签名包括 rapidocr 版本、线程参数和缓存版本常量。
- 持久化到独立文件 `workspace/工作台/ocr-cache.sqlite3`，不写进账本库。服务启动时配置路径；没配置时只用进程内小容量缓存，保证单测不受影响。
- 先查缓存，命中就不进 `_ocr_lock`。识别失败（包括没读出文字）不缓存。缓存行损坏就忽略并重新识别。
- `takeout.inspect_takeout_files`（飞书机器人路径）也改走共享引擎和缓存，不再每批 `RapidOCR()` 新建一次。
- 验收：
  - 单测用假引擎计数：同一字节经不同调用方只识别一次；引擎签名变化时不命中；损坏行会重新识别。
  - 基准：同一张真实截图第二次读取小于 50ms，字段与首次逐项相同。

### T2 上传先保存，后台识别

- 两个上传入口（`web/intake.js`、`web/matching-desk.js`）改为先把本批文件全部 `intake/receive` 保存，然后就可以关闭窗口，不再逐个等识别。
- 服务端新增单线程识别队列：
  - 接收 `{batch, ids}` 入队，逐个调用现有 `prepare_batch_entry`。识别规则、AI 开关和 `force_ai` 语义不变。
  - 新增按批次查询进度的接口（总数、完成、失败、进行中）。
  - 合成台显示“识别中 x/n”。本批识别完成后再执行原有建议组合扫描（`matching.suggest`）并刷新。
- 锁：
  - 队列与手动“重新识别”共用 `intake_run_lock`，队列阻塞等待，手动请求保持现有“正在识别”提示。
  - 不开 AI 时，`/api/intake/prepare` 不再在全局 `write_lock` 内跑 OCR。前提是先确认 `prepare_batch_entry` 的所有写入分支都在 `BEGIN IMMEDIATE` 内校验 revision；不满足就先补齐校验。
  - 旧的 `analyze()` 路径会创建费用，仍保留在写锁内。
  - 手机端 `analyze_local` 同理处理 OCR 与写锁。
- “上传后自动整理”（交给 Agent）分支行为不变。
- 服务中途重启后，未识别的材料不自动重跑（避免启动时意外调用模型），合成台显示“继续识别未完成的 N 份”按钮。
- 验收：
  - 浏览器测试：20 份文件的窗口关闭时间不再随识别耗时增长；识别期间能正常编辑其他材料。
  - 单测：队列串行、重复入队不重复识别、失败计数、重启后显示待续数量。
  - 基准：20 张截图从选择文件到窗口可关闭的时间（目标小于 5 秒），以及识别期间编辑请求的响应时间。

## 阶段 B：准确率

### T3 识别准确率评估脚本（先做，用来衡量 T4–T6）

- 新增 `scripts/eval_recognition.py`，对工作区副本运行。
- 以已核对的台账为标准答案：只取“1 份材料 ↔ 1 笔费用”且费用已核对的样本。对原件重新跑本地提取，逐字段比对金额、发票号码、销售方/商家、类别、日期。
- 输出按材料类型（PDF 发票、截图、行程单）的各字段准确率和覆盖率，写到 `workspace/`，不提交样本内容。
- 验收：在验收报告里给出 T4–T6 前后两次的评估表。

### T4 电子发票二维码交叉校验

- 新增本地模块：
  - 读第一页二维码，依次尝试：页面内嵌图片 → 左上区域 300dpi 裁剪 → 整页 200dpi。
  - 严格解析 `01,类型,代码,号码,金额,日期YYYYMMDD,校验码,...` 格式。
  - 复用 `mail_search.qr_value`；多码时视为不可读，与现有规则一致。
- 在 `_analyze_batch_pdf` 中，对单张发票比对：
  - 号码：始终比对。
  - 日期：比对正文“开票日期”。需要新增本地提取 `issue_date`，它不是消费日期，不能写进 `expense_date`。
  - 金额：相等记为一致。不相等时，类型 31/32（数电票）记为不一致；其他类型的二维码金额可能是不含税金额，记为“未比较”。
- 结果存在材料的 `qr_check` 中：状态（`match`/`mismatch`/`partial`/`unreadable`）、已核对字段、不一致字段、二维码类型。
  - 不一致：加 issue“二维码与正文不一致：<字段>”，必须人工看。
  - 不可读：不加 issue。
- 界面：材料卡片和费用详情显示“二维码核对：号码✓ 金额✓ 日期✓”或红色不一致提示。
- 本轮不做自动核对或一键批量确认，等用户决定。
- 验收：
  - 单测用 `qrcode` 生成合成发票 PDF，覆盖一致、号码不一致、金额不一致、旧类型金额不比较、不可读、多码。
  - 基准：真实样本可读率高于基线 16/25；已核对样本中误报不一致必须为 0；平均耗时小于 0.5 秒/张。

### T5 发票抬头/税号校验

- 公司信息存在本机私有配置 `workspace/工作台/company-profile.json`，格式 `{"names": [...], "tax_ids": [...]}`，允许多个主体。可在设置里提供简单表单。没配置时功能关闭，不产生任何提示。
- 从 PDF 发票定位购买方名称和统一社会信用代码：泛化 `positioned_invoice_seller` 的竖排栏目定位，或复用 `agent_evidence` 的购买方定位。截图发票只在有明确“购买方名称：”标签行时提取。
- 比较前归一化：全半角、空格、中英文括号。
  - 不符：加 issue“发票抬头/税号与公司信息不一致”。
  - 读不到：只在详情里显示“未读取抬头”，不加 issue。
- 测试只用虚构公司名和税号。
- 验收：单测覆盖一致、名称不符、税号不符、未配置、读不到；评估脚本报告真实样本的读取率（在配置了公司信息的副本上）。

### T6 发票商品分类码本地定类

- 新增共享解析：从发票文字解析 `*税收分类*品名` 行，给出（分类集合 → 费用类别、依据）。
  - 只映射不会混淆的分类，例如住宿服务→酒店；铁路客运→高铁；五金、劳保、日用杂品、文具、电线电缆、纸制品等→材料采购。
  - 餐饮服务可能是“餐饮”也可能是“外卖”，不自动定类，只在依据里给出候选。
  - 映射表参考现有 `agent_product_rules`、`transaction_evidence`、`expense_classifier.RULES`，并用工作区副本的真实发票统计校正。统计结果不提交。
- 用在 `_analyze_batch_pdf`：仅当类别仍是“其他”且不是人工字段时设置类别和标题，依据写入 `local_evidence['category']`。`expense_classifier` 解析 `*` 行时也复用这套解析。
- 人工经验优先：`category_experience`、`expense_preferences` 学到的人工选择不能被规则覆盖。
- 不重构 Agent 路径。
- 验收：
  - 单测覆盖映射、混合分类不定类、人工经验优先。
  - 评估脚本：规则给出建议的样本中，类别准确率不低于 95%，同时报告覆盖率。

### T7 识别纠正记录

- 现在 `classify_intake` 和核对编辑会把整张表单的字段都记入 `manual_fields`，原识别值被覆盖。`manual_fields` 的保护语义不改。
- 另外新增本机表 `recognition_corrections`：只记录真正变化的字段，内容为字段、原值、新值、原值来源（native_pdf/local_ocr/glm/...）、时间、材料 ID。
- `scripts/eval_recognition.py` 增加一个汇总：按字段和来源统计人工纠正率。
- 验收：单测确认未改动的字段不记录、改动的字段记录原值和来源、`manual_fields` 行为不变。

## 阶段 D：规模化与开发效率

### T12 打车整理不再全量重扫

- `read_material` 结果按（解析后路径、`st_size`、`st_mtime_ns`、文件 ID `st_ino`）放进进程内缓存。
- 台账附件和文件夹 PDF 先在锁外解析；进入 `BEGIN IMMEDIATE` 后重新读取已用 digest 和附件行，只复用键值仍然匹配的解析结果。新建、补充、重复的结果必须与原实现完全一致。
- 验收：现有打车整理测试全过；新单测确认第二次调用不重复解析未变文件；基准报告启动耗时前后对比。

### T13 读取路径缓存与索引

- 加索引 `events(item_id, id)`。
- `board()` 一次调用只执行一次 `list_items`。
- `expense_identifier_keys` 按（费用 ID、存储数据哈希）缓存。
- `native_trip_pdf`、`native_waybill_pdf`、`source_snapshot` 的读文件结果按（路径、大小、mtime_ns、文件 ID）缓存。文件被替换后必须失效，缺材料确认仍要绑定实时原件。
- 验收：
  - 单测：替换原件后缓存失效、确认失效。
  - 基准：用合成数据生成 1000 笔费用的副本，报告 `/api/state` 和 `board()` 前后耗时。

### T14 并行测试与浏览器测试入口

- 开发依赖加 `pytest-xdist`，修正并行冲突（固定端口、共享路径等），使 `pytest -n auto` 全部通过；串行跑法继续有效，`AGENTS.md` 的交付要求不变。
- 新增 `scripts/run-browser-tests.ps1`（或 `.mjs`）：依次运行全部 `tests/*.cjs`，说明 Playwright 的解析方式，汇总通过/失败并返回退出码。README 开发章节补用法。
- 验收：报告串行与并行的耗时，以及浏览器测试的汇总结果。

## 不做

- 不提高 OCR 线程数（实测更慢）。
- 不开启 SQLite WAL（当前规模收益小）。
- 不增加任何联网验真或云服务；二维码只在本地解码。
- 二维码一致后自动核对或一键批量确认，等用户决定后再做。

### F2 修正核对快捷键抢占 Enter（bug）

- 现象（浏览器已复现）：键盘焦点在“退回待核对”等按钮或链接上时按 Enter，`app.js` 的 keydown 处理调用了 `preventDefault()`，原控件没有响应，反而执行了“核对并下一笔”。
- 修正：焦点在可交互控件上时（`button`、`a[href]`、`summary`、`[role=button]`、`[role=link]`、带 `tabindex` 的控件，列表区 `#list` 和 `body` 除外），Enter 和 E 不触发快捷操作，交给控件本身处理。J/K/方向键保持现状。
- 验收：在 `tests/review_navigation_browser.cjs` 增加两个场景：焦点在按钮上按 Enter 只触发该按钮；焦点在链接上按 Enter 不发起核对请求。

### F3 手工上传路径接入本地铁路电子客票解析（准确率，收益最大）

- 发现：T3 严格样本的 38 份 PDF 发票里有 36 份是铁路电子客票。`_analyze_batch_pdf` 没有铁路票解析，这 36 份只得到“待核对购买凭证”和“金额冲突”，正式环境只能等 GLM 补。
- 项目里已有现成的解析器：`agent_combinations.local_structured_facts`（铁路分支），目前只有 Agent 路径（`agent_tools.py` 的 `_complete_structured`）在用。验收时用它对同一批已核对台账做了离线对比：金额 36/36、类别 36/36、商家 36/36 正确，有标准答案的发票号码 27/27 正确。
- 做法：在 `IntakeQueue._complete_local_special_fields` 中复用它，沿用 `_complete_structured` 的保护规则：人工字段和人工指定的用途不覆盖；已识别出不同金额时不覆盖；只填空字段，或替换占位值（类别“其他”、标题“待核对购买凭证”）；填入金额后去掉“金额冲突”。
- 确认本地字段齐全后，铁路票走现有“本地已确定关键字段，未调用 AI”的分支，不再请求 GLM。
- 验收：
  - 单测：铁路票本地填充；人工字段不被覆盖；退票费识别；金额不一致时不覆盖。
  - 评估脚本：对同一批 45 笔重跑，报告 PDF 发票各字段前后的准确率和覆盖率。目标：金额覆盖率从约 5% 提升到 90% 以上，准确率保持 100%。

### F4 二维码解析兼容带横杠日期

- 原因：T4 剩下 11 张解析失败的二维码中，10 张的日期是 `YYYY-MM-DD` 格式，1 张字段里有多余空格。任务单原先只允许 `YYYYMMDD`，写得过严（任务单的问题，不是执行问题）。
- 做法：`parse_tax_qr` 先去掉每个字段首尾空白；日期同时接受 `YYYYMMDD` 和 `YYYY-MM-DD`，都转成 ISO 格式再比较。其余校验保持严格。
- 验收：单测覆盖两种日期格式和带空格的字段；重跑 `bench-qr.py`，25 份样本可解析数（目标 25/25）、误报 0、平均耗时。
