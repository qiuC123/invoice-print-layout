# 飞书住宿接入方案

2026-09-22。阶段：已完成线上字段及代码只读核查，正在完成第1、2步选型验证，尚未接入生产或部署。

## 目标和已确认范围

后勤工作台面向手机和公司同事使用，以飞书作为入口，住宿记录以现有多维表格为准。用户最新决定：脚本优先，Jev候选负责语义判断，Codex用于开发维护及按需复杂任务，不是日常必经后台。现有报销处理能力继续复用。功能与字段设计见 [住宿功能清单](lodging-functions.md)。

当前授权为功能/字段清单和50条合成样例的规则/Jev实测。没有执行真实住宿登记、表结构调整、权限扩展或服务器部署。

## 当前证据

- 通过既有飞书 CLI，以 user 身份调用 `base +table-get` 成功。线上表为「入住续住登记」，主字段为普通文本「房号（选填）」。这证明当前用户能读取，不证明现有机器人应用能读取或写入。
- 业务输入：房号（选填）、业务类型（新开/续住）、起算日期、入住晚数、每晚单价；结果：应付金额、下次付费日期。金额及日期公式仍兼容旧确认快照，新登记按本行输入计算。
- `base +workflow-get` 确认旧「入住续住：确认后保存快照并更新到期日」仍为 disabled。旧关联与快照字段保留，不恢复旧工作流。
- 表内尚无独立的项目、酒店、入住人员、登记人、来源消息 ID 字段；有备注，但不足以承担可靠的多人检索、范围控制与写入去重。
- `feishu_bot.py` 使用飞书 WebSocket 收消息，先写 DurableQueue，再由单个工作线程执行 BotController；已有单实例保护及消息恢复机制。
- `bot.py:handle` 仅接受已绑定 owner 的单聊；打印批次使用同一 BotInbox 的 current 状态。不能仅删除 owner 校验就开放多人。
- 当前文本处理是固定指令路由，不是 Codex。住宿表 CLI 的 user 授权和机器人 app 凭据是两套接入身份。

## 推荐连接方式

飞书消息 → 接入层确认人员及业务范围 → 持久住宿任务 → 规则解析（必要时Jev判意图）→ 脚本按缺字段追问、业务校验与表格工具 → 回读记录核对 → 飞书返回结果。

1. 复用现有消息接收入口；新增独立住宿路由。旧报销/收件仍保持现有 owner 边界，住宿使用单独的成员和项目范围配置。
2. 住宿会话按应用、会话、发送人隔离；每次写入有独立任务 ID。模型调用不能长期占用当前收件工作线程。
3. Jev只做候选意图判断，不负责业务授权、自由字段抽取和写表。日期、正整数晚数、单价、金额、字段完整性和权限由程序校验；追问由模板生成。任务状态持久保存，不依赖聊天记忆。
4. 新开/续住均要求明确起算日期；房号允许为空。含糊的「续住三晚」先澄清对应住宿与日期，同房号不代表同一酒店或同一次住宿。相对日期按消息时间和北京时间解释并回显。
5. 写入只填业务输入字段，不写公式或历史确认字段，不自动记实付、报销到账或向酒店下单。
6. 对同一来源消息持久去重；写请求超时后先按来源任务标识核对是否已成功，不能盲目重试新增。提交前固化本次内容，追问回复延续原任务。
7. 公司多人版建议增加项目、酒店、入住人员、登记人、来源任务标识，并按实际角色配置数据范围；新增字段先形成具体变更清单，不让旧历史记录被猜填。初期可以先让本人跑通已有字段的登记链路。

## 实施顺序和验收

1. 本地实现住宿业务接口、表格适配器、会话/任务状态及隔离测试，使用合成数据和模拟网关，不创建真实住宿记录。
2. 依据第2步测试决定Jev适用范围，再接入适配器进行受控联调；日常流程不要求Codex常驻。
3. 核实机器人应用的表格访问范围。当前 user 读取成功不替代这一步；缺少权限时明确列出所需范围。
4. 用户本人从手机发一条明确住宿需求，验证缺信息追问、唯一新增、回读金额/日期、重复消息不重复登记、失败可恢复。真实写入以届时具体业务指令为准。
5. 再开放已配置的同事范围，验证跨人会话不串、越权读取/修改被阻止、旧报销收件未受影响；最后部署到选定常开主机。

业务改动交付前按 AGENTS.md 跑完整 pytest 和 mypy；本轮仅文档与只读核查，无业务改动，不重复测试。

## 尚未验证

机器人身份的表格读写权限、Codex 实际调用、多人权限、真实住宿写入端到端、服务器网络与运行依赖均未验证。没有运行历史安装/迁移脚本，也没有发送飞书消息。
