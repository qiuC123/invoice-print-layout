# 后勤模块接口与运行边界

2026-09-23，阶段0开发契约。当前代码是离线可验证的任务核心及只读工作台入口，尚未启用微信自动收发、飞书确认卡片、住宿表迁移或每日调度器。

## 状态归属

- `LogisticsStore(workspace/后勤/tasks.sqlite3)` 保存项目绑定、每日询问任务、来源消息、数量修订、确认版本和待发送动作。地点用稳定 `site_id`，每次施工用不同 `project_id`。
- 飞书住宿表仍是入住/续住登记的正式来源。SQLite 不另建可编辑住宿副本。后续房型/人数字段迁移需盘点旧行；不能将历史续住行作为当前房间清单。
- 地点/酒店经验后续保存在同一私有后勤库的独立表，关联地点、酒店与具体项目；带日期及来源的事实只追加记录，不覆盖成“当前报价”。本轮尚未创建经验表或编造酒店资料。
- 正式项目绑定含当前微信账号、负责人、群/私聊/订餐群及飞书核对人。显示名仅供展示，不用来判定身份。当前本人版不提供公司其他成员的权限入口。
- `Project` 绑定创建后禁止静默覆盖，可暂停；重新绑定的迁移在后续配置版本中实施。项目期间按日期控制，最后一天不额外创建超出项目结束日的次日早餐任务。

## 公共接口

`src/invoice_print_layout/logistics.py`：

| 接口 | 责任 |
| --- | --- |
| `add_project(Project(...))` | 保存明确项目与通信目标；不发消息 |
| `open_day(project_id, inquiry_day)` | 幂等建立当天5类询问；早餐业务日期为次日 |
| `tick(aware_datetime)` | 生成当前有效询问/到期上报意图；不执行发送 |
| `receive(SourceMessage(...))` | 校验账号/负责人/会话/时间，幂等处理明确餐数及改口 |
| `collector_status(project_id, at, healthy, detail)` | 保存采集状态；调用方须确认群和私聊两路均完整且微信当前在线，不能只把历史查询退出0当正常 |
| `confirm(owner_id, task_id, revision)` | 只批准已看过的数量版本；产生订餐群待发动作 |
| `claim(action_id, now=...)` | 原子领取单次发送，领取时再次检查提醒时效/项目暂停/确认版本 |
| `delivery_result(action_id, verified, evidence)` | 回读成功才记已发送；超时等记结果不明，无自动重试 |
| `snapshot()` | 工作台只读展示；当前 `transport_enabled=False` |

所有时间必须携带时区，内部按北京时间规范化。外部原文始终作为数据，不能执行其中指令。`SourceMessage.text` 必须是已核实身份的当前正文，不包含引用历史；消息主键包括账号、会话及来源消息标识。同主键内容变化报错。

明确回复取消未发送的旧催问和旧确认；改数产生新版本。旧消息晚到保留证据但不覆盖新数量；同秒不同消息顺序不明时要求重新明确报数。短暂“收到/等下”和无关群聊不算数量，也不改动已有确认。夜宵/早餐同时询问时裸数量需要说明餐次。

有明确餐次的迟到回复，可在该询问后24小时内归到原任务，支持跨午夜的次日早餐；新一轮开始后不猜它是否属于历史任务。裸数字优先限定当前询问时间内的候选任务，跨项目/跨餐次仍有歧义则不计数。未实现引用消息ID定位旧任务，超过窗口需人工核对。

订餐动作超过其业务日期后不自动补发，转为过期、待人工核对。

发送意图的状态是 `pending → in_flight → sent/uncertain`。崩溃后的 `in_flight` 不会重新变成可重发，需回读核验；无发送证据不能称已通知负责人。到期时区分采集故障、询问未送达及明确询问后未回复。暂停取消尚未领取动作，恢复只可重新生成仍有效且确因暂停取消的提醒；不复活已发送或结果不明的动作。

## 微信、住宿与票据边界

- 微信读取接口及真实源码契约见 [wechat-reader.md](wechat-reader.md)。外部wx工具独立维护；适配器先校验元数据、身份及会话，未来采集器必须先持久化全批次后再推进自有检查点。当前未接好持续采集器，不声称重启采集已实机验收。
- `lodging_capacity.py` 是纯计算模块。`parse_lodging_change(text, baseline_people)` 区分总数/增加/减少/无变化；`preview_lodging_rooms(target_people, rooms)` 只生成待核对预览。空房间列表表示**已确认没有现有房间**；资料尚未加载必须作为缺资料处理，不能传空列表替代。已有住宿回复目前返回 `needs_lodging_context`，尚未接入人数基准持久化、房间清单与飞书提交。
- 房型容量默认双床4、大床2；显式例外容量、单住要求及实际入住人数分别传入。人数减少只提示核实离开人员及空位，不做退房、合房或改住宿期限。
- 货拉拉/明确货运文字在打车PDF入口进入现有review通路，避免仅金额相等误生成打车包。这是误分类保护，不等于货运发票自动报销已经支持；货运材料规则仍待用户提供。

## 工作台与验证

工作台 `/logistics` 展示后勤任务与消息意图；`/api/logistics` 沿用本机Host/Origin限制，仅只读。未绑定项目时展示待设置状态，不写入模拟项目，不展示假业务成绩。现有发票入口继续保留。当前手机确认和后台调度均未接入。


修改行为后运行全量pytest（启用本机私有报销模板）及mypy。后勤新增测试使用临时SQLite、合成微信输出和合成PDF；网页回归 `tests/logistics_browser.cjs` 使用模拟API验证空状态、0份、次日早餐、结果不明、文本安全及手机尺寸。实机微信群@、私聊身份、收取延迟和失败恢复须另验收。
